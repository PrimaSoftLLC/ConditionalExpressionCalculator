# Потокобезопасное вычисление датчиков

Статус: согласован пользователем 2026-11-04.

## Задача и подтверждённые условия

ConditionalExpressionCalculator должен безопасно обслуживать параллельные расчёты
по общему снимку датчиков. Пример пользователя: пять потоков получают один список
сообщений и один калькулятор, каждый считает свой датчик. Через зависимости потоки
могут одновременно вычислять один и тот же SensorI для разных сообщений.

Пользователь подтвердил: настройки, формулы и sensorMap снимка не меняются во время
расчётов. Допустимы изменения LocatorServer. Требуются небольшой расход памяти и
высокая скорость, без последовательного выполнения всех расчётов под блокировкой.

Исходная точка библиотеки: master, commit 7b3b0ba, тег 7.4. Значение 6.1 в pom.xml
не соответствует тегу. LocatorServer подключает com.github.PrimaSoftLLC:
ConditionalExpressionCalculator:7.4.

## Что установлено по коду

- SensorCalculator.replaceTokens записывает параметры сообщения и результаты
  зависимостей в общие EToken формул, собственных и внешних условий.
- ExpressionCalculator уже использует локальный double[] для стека вычислений.
- buildFormula/buildCondition лениво записывают списки в SensorI без синхронизации.
- SensorBunchCalculator через SensorBasicOperations создаёт только карту датчиков;
  SensorCalc хранит обычные, изначально null поля formula и condition.
- FuelSensorDataUtils переиспользует условия других датчиков, получая их через
  SensorCalc.buildCondition.
- Наследники SensorCalc переопределяют calculateValue: ограничения, подстановка
  значений и другие преобразования должны сохраниться при расчёте зависимостей.

## Выбранное устройство

### 1. Значения вычисляются без записи в токены

Добавить путь вычисления выражения с разрешением динамических операндов из текущих
MessageI, sensorMap и значения текущего датчика. Числовая константа берётся из токена;
свойство и параметр — из сообщения; ссылка на датчик — из sensorMap.

Результат разрешения сразу помещается в локальный числовой стек. Отдельного прохода
replaceTokens и копирования токенов нет. Каждый вложенный расчёт имеет собственный
стек. Формулы и условия используют одинаковые правила разрешения значений.

Существующие calculateMath(List<EToken>) и calculateConditional(List<EToken>)
сохраняются с прежней семантикой чтения getValue. Новые перегрузки или внутренний
механизм разрешения не требуют изменений SensorI и существующих его реализаций.
Точная форма внутренних методов остаётся исполнителю; не вводить boxing double
или объект на каждый операнд.

EToken.setValue сохраняется для совместимости старого API, но SensorCalculator
его больше не вызывает. Контракт параллельного использования запрещает внешнее
изменение токенов во время вычисления. Принудительное превращение всего публичного
API EToken в immutable API не входит в задачу.

### 2. Подготовка снимка отделяется от выполнения

Добавить явную операцию подготовки всех датчиков карты, например
SensorCalculator.prepare(sensorMap). Она компилирует формулы и условия всех датчиков,
включая зависимости, до передачи снимка рабочим потокам. Компиляция разрешает имена
по полной карте, но не вычисляет датчики и не обходит граф рекурсивно.

Подготовленные списки сохраняются в датчиках; списки, создаваемые подготовкой,
не допускают структурного изменения. Сохраняются прежние правила: ошибка компиляции
логируется и даёт пустое выражение, а не новую ошибку запуска всего снимка.

Существующие публичные buildFormula/buildCondition остаются явными операциями
подготовки: при наличии списка возвращают его без изменения, при отсутствии
компилируют и сохраняют. Их вызывают до публикации снимка. Одновременная подготовка
и вычисление одного снимка не поддерживается и прямо документируется.

Мой выбор для совместимости вызовов без prepare: вычисление остаётся работоспособным,
но при отсутствии подготовленного списка компилирует выражение только локально,
не вызывает setters и не сохраняет его в SensorI. Это устраняет гонку ленивой
инициализации даже у стороннего SensorI с обычными полями. Цена такого fallback —
повторная компиляция при каждом вызове; быстрый путь требует явной подготовки.
Это намеренное изменение прежнего побочного эффекта автоматического кеширования.
Для ошибочного неподготовленного выражения также возможен повторный лог при каждом
вызове; подготовка сохраняет пустой результат и устраняет повторную компиляцию.

Расчёт читает ссылку на подготовленный список один раз и использует локальную ссылку.
В подготовленном пути нет блокировок, ThreadLocal, глобального кеша, клонирования
датчиков и коллекций значений. Остаётся локальный double[] на вычисление выражения.

### 3. Интеграция LocatorServer

В конструкторе SensorBunchCalculator после super(list) подготовить полную sensorsMap.
Это охватывает и обычный get, и getCacheable сервиса. Подготовка завершается до
возврата конструктора и передачи объекта потокам через executor или кеш.

Все элементы уже должны быть окончательными SensorCalc с нужными наследниками;
последующая замена элементов или изменение конфигурации требует нового снимка.
Сообщения, калибровки и options также не должны изменяться во время чтения.
Ответственность за безопасную передачу снимка и сообщений потокам остаётся вызывающему
коду: executor/concurrent cache или другой механизм happens-before.

Зависимости по-прежнему вызываются через s.calculateValue(message, sensorMap),
с сохранением переопределений SensorCalc. Не обходить этот метод прямым вызовом
статического калькулятора. Результаты зависимостей между вызовами не кешируются.

Внешнее условие FuelSensorDataUtils вычисляется без изменения его токенов.
Значение {x}/{0} берётся из датчика, к которому условие применяется, как и сейчас.
Повторные вызовы buildCondition после подготовки только возвращают готовый список.

## Совместимость и границы

- Сохранить публичные сигнатуры, арифметику, NaN, калибровку, порядок разрешения
  динамических операндов и поведение собственных/внешних условий.
- {x} в формуле сохраняет существующее исходное значение 0; в собственном условии
  получает вычисленное откалиброванное значение; во внешнем — значение, которое
  возвращает текущий путь applyCondition.
- Не вводить короткое замыкание логических выражений, мемоизацию зависимостей,
  изменение обработки циклических ссылок, новую грамматику или новые ошибки.
- Потокобезопасность произвольной пользовательской реализации calculateValue
  или MessageI вне библиотеки не гарантируется автоматически. Сохранить вызовы
  расширений и проверить реальные варианты LocatorServer.
- Не менять модель параллельного запуска задач в LocatorServer.
- Не обновлять прочие зависимости и не мигрировать публикацию библиотеки в рамках
  исправления. Docker-миграция к этой библиотеке без fabric8 не относится.

## Проверки корректности

1. Детерминированно воспроизвести исходную гонку управляемым пересечением двух
   вычислений; без sleep и без надежды на случайный порядок планирования.
2. Проверить формулы, собственные и внешние условия; параметры и свойства сообщений;
   общий зависимый датчик и вложенные зависимости; разные значения {x}.
3. Проверить неизменность значений и структуры токенов после последовательного и
   параллельного расчёта. Проверить, что неподготовленный расчёт не вызывает setters.
4. Проверить предварительную подготовку, повторное использование списков,
   отсутствие компиляции в подготовленном пути, null/пустые и ошибочные выражения.
5. Проверить сохранение пользовательского calculateValue у зависимого датчика.
6. Запустить имеющиеся тесты библиотеки. В LocatorServer добавить узкие тесты
   конструктора снимка и параллельного расчёта реальных SensorCalc, включая внешнее
   условие и наследника с преобразованием результата; запустить относящиеся к ним
   существующие тесты без ненужного полного поднятия инфраструктуры.

## Проверки скорости и памяти

Измерить подготовленный путь до и после на одинаковых данных, одной JVM/JDK и
настройках: прямое выражение, условие, общая зависимость; один и пять потоков.
Использовать прогрев, несколько независимых измерений и потребление результата.
Показать throughput, выделенные байты на операцию и отдельно стоимость подготовки.
Выбор инструмента измерений остаётся исполнителю; инфраструктура benchmark не должна
становиться runtime-зависимостью библиотеки.

Численный SLA пользователь не задавал. Мой критерий: отсутствие устойчивой регрессии
подготовленного однопоточного пути за пределами разброса измерений и отсутствие новых
аллокаций пропорционально числу токенов, кроме уже существующего числового стека.
Если обнаружится воспроизводимая регрессия, разобраться до завершения и явно показать
компромисс. Не обещать линейный рост скорости с числом потоков.
Параллельная старая версия служит только ориентиром затрат: её неверные результаты
не считаются допустимой исходной реализацией. Новая версия обязана проходить проверку
результатов при нагрузке.

## Поставка и порядок дальнейшей работы

Это изменение двух репозиториев с письменным дизайном. После согласования документа
составить план реализации через superpowers:writing-plans.

Сначала библиотека и регрессионные проверки, затем интеграция и измерения. Java/Maven
запускать через mise; библиотеку проверять на совместимом с её Java 11 и Lombok JDK,
LocatorServer — на закреплённом JDK 25. Не повышать Java baseline библиотеки без причины.

Для локальной проверки интеграции использовать отдельную тестовую версию артефакта
под ожидаемыми LocatorServer координатами, не перезаписывать локальную/публичную 7.4.
Точные временные координаты и способ Maven override выбирает исполнитель.
В репозитории LocatorServer не фиксировать зависимость на неопубликованную временную
версию; до реального выпуска изменение версии зависимости остаётся шагом интеграции
релиза. Явно отразить в отчёте, если исходный патч требует ещё не выпущенной библиотеки.
Публикация, создание релизных тегов и деплой не входят в это согласование.
