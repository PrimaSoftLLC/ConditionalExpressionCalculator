# Релизы ConditionalExpressionCalculator через GitHub Packages

Статус: проект для согласования, 2026-11-04. Независимая проверка на достаточность
для планирования завершена: существенных открытых вопросов нет.

## Цель и согласованные решения

Перевести библиотеку с потребления через JitPack на GitHub Packages и принять
цикл aurora-release: разработка в develop, выпуск через master, версия из pom.xml,
тег создаёт CI после публикации, следующая версия начинается после релиза.
Пользователь подтвердил, что сервисам нужны только выпущенные версии, и согласовал
координаты `by.aurorasoft:conditional-expression-calculator`.

Мои предлагаемые решения для согласования: первый релиз 7.5, следующий цикл 7.6;
JDK 25 для сборки при сохранении Java 11 для исполнения; подготовка миграции в этом
репозитории без немедленной публикации и без изменения репозиториев потребителей.

## Исходное состояние

- Репозиторий: PrimaSoftLLC/ConditionalExpressionCalculator, рабочая ветка master.
- Рабочее дерево чистое; локальный master на семь коммитов впереди локального
  origin/master. Эти изменения включают исправления потокобезопасности и измерения.
  Перед интеграцией требуется обновить сведения об origin и проверить расхождение.
- Последний подтверждённый удалённый тег — 7.4; pom.xml содержит устаревшую 6.1.
- Ветка develop и GitHub Actions workflow отсутствуют.
- Старый POM публикует во временный файловый Maven-репозиторий, затем через
  site-maven-plugin отправляет его в ветку mvn-repo.
- Потребители используют JitPack-координаты
  `com.github.PrimaSoftLLC:ConditionalExpressionCalculator:7.4`.
- Компиляция настроена на Java 11; Lombok 1.18.22; JMH — отдельный проект.

## Версия и переход на ветки develop/master

Создать develop от текущего локального master, сохранив имеющиеся изменения.
Подготовку инфраструктуры выполнять на develop либо в рабочей ветке от него.
Не переписывать историю master, существующие теги или ветку mvn-repo.
Новые артефакты в JitPack и mvn-repo больше не являются поддерживаемым каналом
публикации; существующие старые версии не удалять.

В первой миграции применяется legacy-исключение aurora-release: значение 6.1
сохраняется до отдельного релизного коммита `chore: release 7.5`. В нём Maven
versions:set устанавливает 7.5, а `## Не выпущено` становится `## 7.5`.
Затем master fast-forward переводится на релизный коммит; develop получает
`chore: start 7.6` с версией 7.6 и новым разделом `## Не выпущено`.
В следующих циклах версия уже правильная и при выпуске не меняется.

Выпуск выполняется отдельным запросом через aurora-release с учётом инструкции
проекта для библиотеки. Вместо Docker публикуются Maven JAR/POM. README и AGENTS.md
должны явно описывать это отличие. Глобальный skill в рамках миграции не изменяется.
Push в master запускает релиз и не является частью простого согласования дизайна.
Если правила защиты веток требуют PR, использовать принятый PR-процесс, сохраняя
проверку релизного SHA; не обходить ограничения и не применять force push.

## Maven и инструменты

- Единственный источник выпускаемой версии — корневой pom.xml; теги не задают её.
- distributionManagement указывает на
  `https://maven.pkg.github.com/primasoftllc/conditionalexpressioncalculator`.
  Единый id для публикации, потребления и settings.xml — `github-conditional-expression-calculator`.
- Удалить site-maven-plugin, файловый altDeploymentRepository и неиспользуемое
  github.global.server. Настроить актуальный фиксированный Maven Deploy Plugin.
- `package`, `verify`, `install` не публикуют ничего. Публикация — только явный
  `deploy` в релизном CI; не добавлять публикацию в ранние фазы lifecycle.
- Публикуются основной JAR и POM с зависимостями. Добавление sources/Javadoc JAR
  не требуется для этой миграции. Метаданные основного JAR включают версию и полный
  Git SHA для проверки происхождения; SHA не влияет на номер Maven-версии.
- mise.toml: Temurin 25.0.4+7.0.LTS и Maven 3.9.16. Wrapper Maven 3.9.16,
  only-script, без wrapper JAR. В CI setup-java Temurin 25 и cache maven.
- Использовать `maven.compiler.release=11`, обновить Lombok до версии с поддержкой
  JDK 25 и явно указать annotation processor. Точные версии build-плагинов выбирает
  исполнитель после проверки совместимости. Runtime-зависимости не обновлять заодно.
- Добавить .gitattributes, .mvn/maven.config с `-ntp` и
  `-Daether.enhancedLocalRepository.trackingFilename=_ignored.repositories`.
- Добавить .Codex/settings.json и guard-bash.sh по стандарту пользователя, с запретом
  агентской публикации (deploy/docker push) и разрешением сборочных команд.
  В эталонном gateway файлы сейчас находятся в .claude, а не в .Codex; адаптировать
  их в требуемый каталог и не объявлять hook действующим без проверки поддержки
  текущей средой. CI этим локальным hook не ограничивается.
- Docker, образы и HEALTHCHECK для этой Java-библиотеки не нужны.

## CI и защита от повторной публикации

Один `.github/workflows/ci.yml`, ubuntu-latest, concurrency по ветке.
Новые проверки develop/PR могут отменять старые; выполняющийся релиз master
не отменяется. PR имеет только чтение, без публикации и без секретов для загрузки.

| Событие | Действие |
| --- | --- |
| PR в develop/master | `./mvnw -B verify`, без deploy |
| push в develop | `./mvnw -B verify`, без deploy |
| push в master | Проверки релиза, verify, deploy, проверка скачивания, тег |

Обычный workflow_dispatch для публикации не нужен; повторный запуск существующего
workflow подчиняется тем же проверкам. Публикация SNAPSHOT и DEV отсутствует.

Релизный job использует GITHUB_TOKEN с `packages: write` и `contents: write`;
setup-java настраивает server id, соответствующий POM. Отдельный PAT для записи
пакета из собственного репозитория не требуется, если это разрешено политикой
организации. Перед первым выпуском проверить права Actions и создание тегов.

Перед deploy проверить: версия числовая X.Y[.Z], не SNAPSHOT; в CHANGELOG есть
непустой раздел точно этой версии и нет незакрытого `## Не выпущено`; теги
`v<version>` и исторический `<version>` отсутствуют; соответствующая Maven-версия
ещё не опубликована. Проверять registry с аутентификацией. Отсутствие версии
отличать от отказа доступа, сетевой ошибки и 5xx; ошибки проверки останавливают
публикацию. Нельзя трактовать любой неуспешный запрос как свободную версию.

Релиз собирается и проверяется на точном SHA события. После verify выполняется
deploy этого же исходного состояния. После deploy скачать POM и JAR с помощью
отдельного чистого Maven-кеша и сравнить координаты, версию, SHA и содержимое JAR
с опубликованным кандидатом. Затем CI создаёт тег `v<version>` на релизном SHA.
GitHub Release с заметками не входит в обязательный результат: достаточно пакета,
тега, CHANGELOG и ссылки на workflow. Теги люди и локальный агент не создают.

Если публикация успешна частично либо пакет появился, а тег создать не удалось,
workflow завершается ошибкой и показывает конкретный этап. Обычный повторный
запуск не перезаписывает и не удаляет пакет. Исправление такого инцидента — отдельное
действие после проверки registry и SHA: завершение тегирования через проверенный
CI либо следующий номер версии. Автоматическое восстановление частичного выпуска,
удаление опубликованных версий и специальный recovery workflow в эту миграцию
не входят. README обязан описывать это ограничение и запрет слепого повторного deploy.

## Подключение потребителей и JMH

README содержит готовый пример новой зависимости, repository URL с отключёнными
snapshots и settings.xml с одноимённым server. Для локального скачивания и CI
потребителей используется PAT classic с read:packages и доступом к репозиторию;
секреты передаются переменными среды, не сохраняются в Git. Пример для CI использует
имя GH_PACKAGES_TOKEN. Наличие доступа к новому пакету проверяется до переключения
сервисов. Заменить нужно координаты, версию и repository, а не только номер версии.

Репозитории LocatorServer и других сервисов не меняются в этой задаче.
README явно говорит, что существующие потребители 7.4 останутся на старой библиотеке
до отдельного обновления, включая отсутствие исправлений потокобезопасности.

Исторические JMH-результаты и инструкции baseline остаются воспроизводимыми.
В benchmarks добавить выбор координат через свойства: по умолчанию новый groupId
и artifactId, версия берётся явно из установленной локально сборки корневого POM;
для старых измерений документировать переопределение всех трёх координат. Не
превращать benchmarks в публикуемый модуль и не вводить его версию как вторую
версию библиотеки. Локальный install для измерений допустим и не является
публикацией SNAPSHOT в GitHub Packages.

## Проверка и граница готовности

До запроса на выпуск выполнить clean verify на JDK 25 и дополнительную проверку
совместимости на JDK 11; проверить class-file version 55, публичный API и работу
Lombok/Jackson в имеющихся тестах. Проверить effective POM и локальный install
по новым координатам, сборку JMH с новой зависимостью и сохранность старого пути.
Проверить workflow статически и отдельно сценарии guard: существующий тег/пакет,
SNAPSHOT, отсутствующий раздел changelog, отказ доступа и ошибка сети. Для HTTP
использовать подставные ответы, без публикации пробных пакетов в registry.

Готовая реализация — изменения POM, CI, инструментов, инструкций и CHANGELOG,
прошедшие локальные проверки. Первый push в master и фактическое скачивание
опубликованной 7.5 проверяются только при отдельно разрешённом первом выпуске;
до него не утверждать, что публикация или права организации проверены.
