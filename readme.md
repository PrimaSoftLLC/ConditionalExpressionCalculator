# ConditionalExpressionCalculator

Java-библиотека для вычисления арифметических выражений и логических условий,
в том числе по данным телеметрии. Позволяет описать датчик формулой, использовать
параметры сообщения и значения других датчиков, применить калибровку и отфильтровать
результат по условию.

Выражение преобразуется в обратную польскую запись — список токенов, который можно
подготовить один раз и использовать для последующих расчётов. Библиотека работает
внутри приложения, без отдельного сервера. Минимальная версия Java — 11.

## Быстрый старт

Для выражений с числами достаточно `ReversePolishNotation` и `ExpressionCalculator`:

```java
import by.aurorasoft.expressioncalculator.ExpressionCalculator;
import by.aurorasoft.expressioncalculator.ReversePolishNotation;
import by.aurorasoft.expressioncalculator.model.EToken;
import java.util.List;

List<EToken> formula = ReversePolishNotation.create("(6+10-4)/3", List.of());
double value = ExpressionCalculator.calculateMath(formula); // 4.0

List<EToken> condition = ReversePolishNotation.create("10>0&100<120", List.of());
boolean matches = ExpressionCalculator.calculateConditional(condition); // true
```

Пустой список во втором аргументе означает, что выражение не ссылается на датчики.
Для проверки пользовательского ввода используйте `ExpressionChecker.checkMath`
или `checkLogic`: они возвращают строку без лишних пробелов вне фигурных скобок
и выбрасывают `IllegalArgumentException` при ошибке. Это методы экземпляра:
`new ExpressionChecker().checkMath("2 + 2")` вернёт `"2+2"`.
При прямом вызове `ReversePolishNotation.create` передавайте выражение без пробелов
вне имён датчиков.

## Синтаксис выражений

| Элемент | Запись | Пример |
| --- | --- | --- |
| Числа | Целые и десятичные с точкой | `12`, `3.5` |
| Арифметика | `+`, `-`, `*`, `/` | `2+3*4` |
| Бит числа | `bit(число, индекс)` | `bit({@flags},3)` |
| Сравнения | `>`, `>=`, `<`, `<=`, `=`, `!=` | `10>=5` |
| Логическое И / ИЛИ | `&` / `\|` | `(10>5)&(2<3)` |
| Группировка | `(`, `)` | `(2+3)*4` |
| Свойство сообщения | `{#имя}` | `{#speed}` |
| Параметр телеметрии | `{@имя}` | `{@fuel}` |
| Другой датчик по имени | `{имя датчика}` | `{Fuel level}` |
| Текущее значение | `{x}` | `{x}>0` |

Приоритеты от старшего к младшему: `*` и `/`, затем `+` и `-`, сравнения,
затем логические операции. У `&` и `|` одинаковый приоритет; явно задавайте
нужную группировку скобками. Логические операции не используют короткое замыкание.
Для отрицательного числа используйте вычитание: `(0-10)`.

Доступные свойства сообщения: `latitude`, `longitude`, `altitude`, `speed`,
`amountSatellite`, `course`, `gpsOdometer`, `gsmStrength`, `battery`,
`batteryVoltage`, `onboardVoltage`, `ecoAcceleration`, `ecoBraking`,
`ecoCornering`, `ecoBump`.

Имена датчиков сопоставляются без учёта регистра. В исходной строке `{123}`
означает датчик с **именем** `123`, а не поиск по ID. При подготовке выражения
имена заменяются внутренними ссылками на ID датчиков.

### Функция bit

`bit(число, индекс)` возвращает числовое значение `0.0` или `1.0`.
Нумерация начинается с младшего бита: допустимы индексы **0–63**.
Число должно быть конечным целым в диапазоне **[−2⁵³, +2⁵³] включительно**
(от −9007199254740992 до 9007199254740992), индекс — конечным целым от 0 до 63.
После проверки число преобразуется в Java `long`, результат вычисляется как
`((long) число >>> индекс) & 1L`. Индексы за границами диапазона не зацикливаются.

Функция принимает ровно два числовых выражения: константы, ссылки на параметры,
свойства и датчики, арифметику или вложенные вызовы `bit`. Имя пишется как `bit`.

```text
bit({@flags},3)                   // бит 3 параметра flags
10*bit({@flags},3)+2              // число для арифметической формулы
bit({@flags},3)=1 & {#speed}>0    // логическое условие
bit(4+4,1+2)                     // 1
bit(bit(8,3),0)                  // 1
bit((0-1),63)                    // 1
```

Комментарии справа приведены для пояснения и не входят в синтаксис формул.
Пробелы вне фигурных скобок удаляет `ExpressionChecker`; при прямом вызове
`ReversePolishNotation.create` передавайте строку без них.
Результат `bit` — число, поэтому в условии нужно сравнение, например `=1` или `=0`.
Операторы `&` и `|` остаются логическими, с одинаковым приоритетом и без короткого
замыкания; побитовыми операторами они не становятся.

Исходная разрядность значения неизвестна. Отрицательный `byte -1` при переходе
к `long` сохраняет знак: все 64 бита равны единице, включая бит 8.
Поэтому `bit((0-1),8)` даёт `1`, а `bit(255,8)` — `0`. Если нужны биты
беззнакового байта, вызывающая сторона должна заранее преобразовать его,
например через `Byte.toUnsignedInt(flags)`.

При прямом разборе и проверке неверное число аргументов отклоняется через
`IllegalArgumentException`; при вычислении такое же исключение вызывают дробные
значения, `NaN`, бесконечности и выход за диапазон. `ExpressionChecker`
проверяет синтаксис, числовые типы аргументов и значения константных выражений;
значения параметров, свойств и датчиков проверяются при расчёте. В частности,
отсутствующий параметр (`Double.NaN`) внутри `bit` приводит к исключению,
в том числе при расчёте через `SensorCalculator`.
Ошибки синтаксиса при подготовке `SensorCalculator` обрабатывает как раньше:
логирует ошибку и использует запасной результат, описанный ниже в разделе
«Расчёт датчиков». Проверяйте пользовательские формулы через `ExpressionChecker`
перед сохранением.

Числовой API библиотеки использует `double`: ограничения проверяются для уже
полученного значения. Потерю точности при более раннем преобразовании из `long`
или десятичного текста функция восстановить или обнаружить не может.

## Расчёт датчиков

`SensorI` описывает датчик, а `MessageI` — сообщение с телеметрией. Можно реализовать
эти интерфейсы в своей модели или использовать `SensorImpl` и `MessageImpl`
из пакета `by.aurorasoft.expressioncalculator.model.sensor.impl`.

Пример настройки датчика; `message` — ваше сообщение, реализующее `MessageI`:

```java
import by.aurorasoft.expressioncalculator.SensorCalculator;
import by.aurorasoft.expressioncalculator.model.sensor.impl.Calibration;
import by.aurorasoft.expressioncalculator.model.sensor.impl.SensorImpl;
import java.util.Map;

SensorImpl sensor = new SensorImpl(
        1L, "Fuel level", 100L, new Calibration(),
        "{@fuel}*0.1", "{x}>=0", Map.of());
Map<Long, SensorImpl> sensors = Map.of(sensor.getId(), sensor);

SensorCalculator.prepare(sensors);
double fuelLevel = SensorCalculator.calculateValue(sensor, message, sensors);
```

При `message.getParams()`, равном `"fuel:250,temp:18"`, результат будет `25.0`.
Стандартный разбор параметров ожидает пары `имя:число`, разделённые запятыми;
отсутствующий или нечисловой параметр даёт `Double.NaN`.

Расчёт выполняется в три шага: формула → калибровка → условие. Пустая
`new Calibration()` оставляет значение без изменений; калибровка по точкам
`RawData` использует линейные участки и продолжает крайние участки за диапазон точек.
Если условие ложно, `calculateValue` возвращает `Double.NaN`.
Для получения значения без проверки условия есть `calculateWithoutCondition`.

В карту нужно включить все зависимые датчики. Ошибка подготовки формулы логируется,
и расчёт использует исходный `0` с последующей калибровкой; ошибочное условие
логируется и не ограничивает результат. Проверяйте выражения до сохранения
конфигурации, чтобы не принимать такой результат за корректное измерение.
Особенности `{x}` и совместного использования датчиков описаны в разделе
[«Параллельные вычисления»](#параллельные-вычисления).

## Сборка

Инструменты фиксируются в mise.toml: Temurin 25 и Maven 3.9.16.
После `mise trust` и `mise install`:

```powershell
mise exec -- mvn -B clean verify
mise exec -- mvn -B install
```

CI использует `./mvnw -B verify`. Wrapper only-script, без JAR в репозитории.
Артефакт сохраняет совместимость с Java 11. `package`, `verify`, `install`
не публикуют пакет. Manifest содержит Implementation-Version и Build-Revision.

## Подключение из GitHub Packages

Первый выпуск в GitHub Packages — 7.5. Для подключения заменить
JitPack-координаты и добавить repository:

```xml
<repositories>
  <repository>
    <id>github-conditional-expression-calculator</id>
    <url>https://maven.pkg.github.com/primasoftllc/conditionalexpressioncalculator</url>
    <releases><enabled>true</enabled></releases>
    <snapshots><enabled>false</enabled></snapshots>
  </repository>
</repositories>
<dependencies>
  <dependency>
    <groupId>by.aurorasoft</groupId>
    <artifactId>conditional-expression-calculator</artifactId>
    <version>7.5</version>
  </dependency>
</dependencies>
```

Для скачивания нужен PAT classic с read:packages и доступом к репозиторию
(при необходимости авторизованный для SSO организации). Пример server для
локального ~/.m2/settings.xml и CI потребителя:

```xml
<settings><servers><server>
  <id>github-conditional-expression-calculator</id>
  <username>${env.GH_PACKAGES_USER}</username>
  <password>${env.GH_PACKAGES_TOKEN}</password>
</server></servers></settings>
```

В CI потребителя GH_PACKAGES_USER задаётся именем пользователя GitHub,
GH_PACKAGES_TOKEN — секретом с read:packages. Токен не сохраняется в Git.
Прежние потребители `com.github.PrimaSoftLLC:ConditionalExpressionCalculator:7.4`
остаются на старой версии, включая старое поведение параллельных расчётов,
пока их зависимость и настройки repository не будут обновлены отдельно.

## Релиз и версии

Разработка ведётся в develop. Версия в корневом POM — разрабатываемая;
теги не определяют версию. PR в develop/master и push develop запускают
тесты. Только push master публикует Maven JAR/POM в GitHub Packages.
SNAPSHOT и DEV-сборки не публикуются.

Используется `/aurora-release 7.5` с адаптацией для библиотеки: вместо Docker
CI выполняет Maven deploy. Перед первым выпуском проверить разрешения Actions
на packages:write, contents:write и создание тегов по правилам организации.
Для публикации своего пакета CI использует встроенный GITHUB_TOKEN, не PAT.

Первый переход является legacy-исключением: POM ещё содержит 6.1, хотя последний
исторический тег — 7.4. В `chore: release 7.5` команда Maven versions:set
устанавливает 7.5 и раздел `Не выпущено` закрывается как `7.5`. После проверки
`mise exec -- mvn -B verify` и согласования релизной сводки master fast-forward
переводится на этот коммит. Develop получает `chore: start 7.6` с новым разделом
`Не выпущено` и версией 7.6. В дальнейшем bump происходит только после выпуска.
Уважать branch protection; не использовать force push и не обходить проверки.

CI блокирует уже существующие теги `vX.Y` и `X.Y`, опубликованную или частично
опубликованную Maven-версию, ошибки доступа и незакрытый CHANGELOG. После verify
он публикует пакет, скачивает JAR/POM в чистый Maven-кеш, сверяет хеши и Git SHA,
затем создаёт тег `vX.Y` на проверенном коммите. Люди теги вручную не создают.
Глобальный aurora-release skill не изменяется; эта инструкция задаёт вариант
для библиотеки. Локальная публикация агентом запрещена.

Если пакет уже появился, а скачивание или тегирование завершилось ошибкой,
не повторять deploy вслепую, не удалять пакет и не перезаписывать версию.
Проверить последний успешный шаг CI, POM/JAR в registry и SHA. Завершение
тегирования через проверенный CI либо выпуск следующего номера — отдельное
действие после разбора. Автоматического recovery workflow нет.

Проверка CI-логики без публикации:

```powershell
python -m unittest discover -s .github/scripts/tests -v
```

## Параллельные вычисления

Создайте полную карту датчиков и подготовьте её до передачи рабочим потокам:

```java
SensorCalculator.prepare(sensorMap);
// Далее передавайте снимок задачам через ExecutorService или concurrent cache.
double value = SensorCalculator.calculateValue(sensor, message, sensorMap);
```

Вычисление читает токены и использует локальный числовой стек. Значения параметров,
свойств, зависимостей и `{x}` не записываются в общие токены. Переопределения
`SensorI.calculateValue` сохраняются для зависимых датчиков.

Без подготовки выражение компилируется локально при каждом вызове; прежнего
автоматического кеширования во время расчёта больше нет. Ошибочное выражение без
подготовки также будет повторно логироваться. `buildFormula` и `buildCondition`
остаются явными операциями подготовки, вновь созданные списки неизменяемы.

Не изменяйте sensorMap, конфигурацию, калибровки, options, сообщения или токены во
время расчётов; подготовка не должна пересекаться с вычислением. Безопасную передачу
снимка потокам обеспечивает вызывающий код. Собственные реализации SensorI/MessageI
также должны поддерживать параллельное чтение. Старый API ExpressionCalculator
продолжает читать значения, заданные через EToken.setValue.

`{x}` в формуле равен исходному 0; в собственном условии — откалиброванному значению,
во внешнем условии — значению целевого датчика. Логические операнды вычисляются без
короткого замыкания; результаты зависимостей не кешируются.
